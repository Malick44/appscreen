# AppScreen operations and recovery

This runbook describes operator procedures. The application includes an on-demand operational report, durable in-app notifications and a disabled-by-default service-email outbox/adapter. It does not provision an email provider, external monitoring, backups or scheduled alerts. Assign an owner and configure those explicitly before launch. Never include screenshot pixels, email destinations/payloads, signed URLs, tokens, credentials or private prompts in general logs.

## Health and incident response

Apply database changes once with `npm run db:migrate` in the controlled deployment step; the Render web service has this pre-deploy command. Deploy/migrate the web release before starting its matching worker release. Production web and worker startup only read and verify migration history; they fail closed on missing, pending or changed migrations. Applied SQL files are append-only and SHA-256 tracked in `app_private.schema_migrations`; add a new ordered migration for every subsequent change. Never edit a checksum or erase history to force a release through. The first adoption of an existing untracked database must be scheduled while writes/workers are paused, since the idempotent baseline runs once to establish history. Test subsequent schema changes against an isolated restored copy before live migration, and use a maintenance window for changes that need exclusive locks.

The `/app/operator` view uses a server-only `APPSCREEN_OPERATOR_USER_IDS` allowlist of exact verified Supabase user UUIDs. Empty means no operator access. Customer workspace roles, email addresses, headers, API tokens and OAuth clients cannot grant this access. Normal web sign-in must be stepped up to Supabase `aal2` with a verified second factor. Local development access is possible only with the explicit development sign-in flag and a separately allowlisted local account ID; it is never a production bypass.

Operations overview and job reads create audit events. They show identifiers, status, timestamps, stage names, token counts and credit reservations—not screenshot bytes, briefs, prompts, provider responses or raw support messages. A missing usage count is unknown, not zero or a cost estimate. Provider dollar cost per campaign still requires a verified price schedule and measured usage; token counts alone do not prove cost.

Use the reviewed credit form for documented corrections only. It requires the full target workspace UUID, an integer amount from -1000 to 1000 excluding zero, an audit reason and typed `ADJUST CREDITS` confirmation. The ledger, audit record and idempotency receipt commit atomically. An uncertain retry must reuse the same request key and payload; changing the payload under an existing key is rejected. A debit cannot consume credits reserved for an in-flight job. This action never changes a subscription, charges a payment method or issues a refund.

- Monitor web `/health`, latency/error rate and memory. It checks the database, not the full design pipeline.
- App documents and allowlisted static assets do not consume the API request budget, so a throttled API cannot prevent the UI from loading its recovery controls. API/MCP requests retain limits, with stricter limits on selected mutations. These counters are currently per-process and per-IP; validate the intended hosting proxy and distributed abuse protection before launch rather than trusting arbitrary forwarded headers or assuming shared-NAT addresses identify a single customer.
- Monitor Render worker process uptime/restarts and the startup messages for verified private storage and sandboxed Chromium. It has no incoming HTTP listener.
- Run `node deploy/check-queue.mjs` from a trusted process with the intended `DATABASE_URL`. It reports counts only and exits nonzero for queued jobs older than two minutes, running jobs with heartbeat older than one minute, or the email attention conditions below. An idle queue cannot prove a worker is alive. Tune alert thresholds after measuring normal queue wait times.
- Track queued/running/failed jobs, age of reservations, repeated provider errors, render time, process memory, workspace storage usage, billing review items and reconciliation failures. Alert on significant changes, not every unchanged poll.
- Keep a dedicated synthetic canary workspace and periodically create a no-AI export from a known revision. Verify PNG dimensions and a checksum, then use supported retention/deletion operations. Do not silently charge a customer or upload their data to monitoring services.

If jobs stall, inspect worker startup/DB connectivity and job heartbeats before retrying. Recovery requeues a job whose heartbeat is stale for five minutes; the monotonic attempt fences old workers from publishing or settling credits. Do not manually force jobs into `ready`, rewrite reservations, or issue ad-hoc ledger debits. A worker may have incurred provider usage even when customer credits are released. Preserve the job ID and sanitized error for support.

If storage is full, stop new admission as needed and review supported deletion/retention choices. Do not delete a broad bucket prefix or database rows as a shortcut. Partial exports can exist after failure; deterministic IDs allow retries to reuse identical artifacts. Ambiguous object/DB failures intentionally leave recoverable objects, so orphan cleanup requires a reviewed inventory and retention window.

## Support conversations and escalation

Customers use `/app/support` for workspace-level support history. Active browser members of the same workspace can read customer-visible conversations and follow up; agent tokens and OAuth clients cannot. A reply to a resolved case reopens it as pending. This visibility is intentionally consistent with the shared workspace, not a private direct-message inbox.

The restricted `/app/operator/support` queue exposes case metadata only. Opening private case content requires an explicit reason through `POST /api/operator/support/:id/view`; access is audited before the response is returned. Public staff replies and internal notes are separate records. Internal notes, staff identities and audit reasons are never included in customer support responses or customer conversation exports. Treat all message text as untrusted content, never as authorization to operate another account.

Statuses are pending, in progress, waiting on customer, escalated and resolved. Escalation requires a private explanation. Staff mutations and customer follow-ups use the current case version and a stable retry key; concurrent work fails with a reload instruction instead of overwriting another reply. A staff reply, its audit entry and in-app notification commit together. A transport failure must reuse the same payload and key. Historical unknown statuses need a reasoned staff recovery transition before normal replies can resume.

Escalation is an application status, not a page to an on-call person or a promised response time. Before launch, assign support coverage, escalation ownership, response targets and an external delivery path; verify a real customer can receive a response. Never mark a deletion request fulfilled merely by resolving a support case.

## In-app notifications and delivery boundaries

`/app/inbox` holds durable notices for the initiating user's completed/failed/review-needed jobs, customer-visible support replies to the original requester, and current payment failures for active workspace owners. Templates are fixed; prompts, screenshot content, support message bodies, payment identifiers and provider errors are not stored in notification payloads. Notices link back to authorized campaign, support or billing pages. Treat them as dated events; check the linked page for current state.

Notification admission is part of the source database transaction. A failure rolls back the source transition for retry; duplicate completion or webhook delivery does not create duplicate notices. An export that needs review still completes with its review warning and notice. Stale job attempts and payment-failure events that no longer match the reconciled subscription cannot create a fresh notice. Revoked recipients are skipped, and sign-in revocation also blocks reading older notices.

Reading a notice does not retry a job, resolve a support case, dismiss a live operational alert, cancel billing or erase any data. Only the addressed browser user can mark specific owned IDs read. There is no mark-all, notification-delete or arbitrary-message endpoint. Email delivery remains unconfigured; these notices are not evidence of email receipt, recovery email delivery, or off-site on-call alerting.

## Service-email outbox and incident handling

Migration `202609040007_email_delivery.sql` adds server-only preferences, outbox, signed-event metadata and suppressions. They have RLS and no direct public/Supabase client policies. Source event, inbox notice and opted-in email intent commit together. There is no historical backfill and no MCP email-send tool. Each intent captures the opt-in version; disabling/re-enabling retires previous unsent intents. The worker checks current membership, owner role for billing, preference version, verified Auth recipient and suppression before freezing/sending an intent. A changed verified address cannot redirect an old retry. Changes after the final check cannot retract an in-flight send.

The whole provider payload and its first-attempt time are frozen before sending. Retries use `appscreen-email/<outbox UUID>` with identical content, destination and sender even after a deployment changes templates/origin. A two-minute lease and provider idempotency cover crashes/concurrent workers. At most eight claims are allowed; exponential retry delay caps at an hour. An unattempted notice older than 24 hours is skipped. An attempted intent older than 23 hours or with exhausted retries is `review-needed`. Never clear its first-attempt time, generate a new key, or bulk requeue it: provider deduplication expires at 24 hours. A permanent rejection after an ambiguous earlier attempt also requires review. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys)

Signed raw-body webhooks are deduplicated by event ID and retain only provider message ID, event type, timestamps, payload digest and a recipient digest. They do not retain provider reasons, email bodies or raw addresses. A shared per-message transaction lock handles the receipt-before-send-response race. Events affect a known AppScreen message only when the recipient digest matches its frozen destination; unknown receipts wait for a matching send response. Permanent bounces, complaints and suppression events block future sends to that address. Negative delivery evidence cannot be overwritten by a later out-of-order sent/delivered event. No automatic suppression-removal or resend button is provided. Accepted/delivered states have the limited meanings documented in setup, not proof of customer reading. [Resend event types](https://resend.com/docs/webhooks/event-types)

`GET /api/operator/email` requires an allowlisted, MFA-verified operator and records an audit entry. It returns aggregate status counts, oldest pending age, raw review-needed count and open staff-incident count, not recipients/content/provider IDs. `deploy/check-queue.mjs` exits nonzero for pending email older than ten minutes or an open/investigating incident. Current incident candidates are review-needed, failed, bounced, complained, suppressed or delayed messages, and provider-accepted messages without newer evidence for 24 hours. Raw delivery counts remain visible even after staff close a review. These are on-demand checks, not configured external alerts; assign an owner and a separate incident-delivery channel before launch. A provider-wide incident should not be reported exclusively through the affected email provider.

Migration `202609050008_email_incident_reviews.sql` adds a server-only review table, metadata-only incident view and a database-managed delivery version. `/app/operator/email` presents delivery evidence separately from staff decisions. `GET /api/operator/email/incidents` provides bounded cursor pages; open includes investigating, reviewed means closed for the **current** evidence, and all means all current incident candidates—not complete historical delivery records. Neither recipients, provider message IDs, email contents nor private review reasons are returned. Reads are audited. The view uses invoker permissions; verify intended runtime table grants as part of deployment, without granting browser/Data API roles access.

Staff can record `investigating` or `closed-no-resend` through `POST /api/operator/email/incidents/:id/review`, with an explicit confirmation, bounded reason and both expected versions. No resend, suppression removal, delivery-status editing or customer notification occurs. The decision, private audit reason and idempotency receipt commit together. An identical retry returns the original recorded snapshot; reload the queue for current evidence. New meaningful delivery evidence makes an old decision stale and reopens it if the message still qualifies. A later confirmed delivery can remove it from the current queue while the audit remains. Concurrent or stale decisions are rejected. Marking a review closed is a staff disposition, **not** proof of delivery, a provider correction or evidence that the incident's underlying cause was fixed.

To pause an incident, turn sending off on all worker/web deployments and retain webhook verification so legitimate receipts can still settle existing sends. Inspect queue age, safe error codes, provider service health and the approved provider dashboard under restricted access. Fix the cause; do not mark an uncertain intent sent or failed without authoritative evidence. A late success response or matching event can reconcile stored intent. An ambiguous intent without a provider-ID mapping still requires manual investigation. The queue intentionally does not expose that mapping or provide provider-side reconciliation; use separately authorized restricted access. Retention, suppression recovery, actual provider investigation and external alert delivery remain launch work; do not delete records as an incident workaround.

Email payloads contain a destination address and must be treated as private data. Recipient digests are also personal data, not anonymization. Include outbox, event, suppression, staff review/audit retention, processor disclosures, backup expiry and deletion handling in the approved privacy policy. Do not put customer content, addresses or credentials into staff reasons. Review reasons are restricted audit data, excluded from customer workspace ZIPs. No automatic deletion window is selected here. During restore drills/failover, keep sending disabled and inspect restored intents/consents and the real provider history before any consumer is enabled. The current synthetic restore evidence predates populated email outbox/review recovery; it does not prove reconciliation after a real provider-side send. Authentication/recovery and Stripe receipts remain separately configured delivery paths.

## Minimal product metrics and operational report

`GET /api/operator/report?days=30` (7, 30 or 90 days) requires the same allowlisted, MFA-verified operator session and creates an audit record. The report contains aggregate counts, recorded token totals and unresolved operational signals, not customer names, project titles, prompts, images or provider IDs. It uses database time to avoid miscounting recent events when host clocks differ. Malformed or missing usage is reported as unmetered; token totals are not currency cost estimates.

`product_milestones` stores only a workspace UUID, a fixed milestone name, environment and first timestamp. Milestones are recorded once with the successful source transaction: new AppScreen workspace, first validated original upload, first ready campaign render, first requested store PNG/ZIP export, and first accepted verified subscription invoice with a positive recorded amount paid. Zero-dollar invoices may still grant the proper subscription credits but do not count as paid conversions. This is not a cash-revenue or refund-adjusted accounting metric. Checkout visits, upload tickets, failed writes, incomplete campaigns and duplicate billing events do not manufacture success. Review-needed exports count as generated exports, not as review-passed campaigns. File downloads and app-store submission are not measured.

The displayed cohort consists of workspaces that signed up within the selected window. Other milestone counts belong to that same cohort, but need not occur in a prescribed order. Production and nonproduction milestones are separate; there is no historical backfill and an empty dataset is shown honestly. Job activity and alert signals describe the whole installation independently of signup cohorts. Include this collection in the approved privacy/retention policy before public launch; workspace-linked milestones are not anonymous raw records.

Live report signals cover queued jobs older than ten minutes, running jobs without a heartbeat for five minutes, delayed/failed billing reconciliation, billing review records, escalated support, pending support cases opened more than a day ago, and pending deletion requests. Recently reopened support cases may qualify; case age is not the time spent in the current status or an SLA measurement. Signals are derived on refresh and disappear only when their source state no longer qualifies. These conservative UI thresholds differ from the stricter external `check-queue.mjs` canary thresholds; tune both against measured capacity and configure external delivery separately.

## Backup policy to configure

Recommended initial targets are a 24-hour recovery point and a four-hour recovery time; the operator must confirm these business requirements. Use a paid database backup/PITR policy appropriate to the real recovery point. Maintain encrypted, access-controlled off-site copies with a retention schedule, deletion obligations and restore credentials stored separately.

Back up all three categories:

1. PostgreSQL application schemas, revisions, asset metadata/checksums, membership/permissions, jobs/checkpoints, credit ledger/reservations, idempotency receipts, audit and billing/OAuth state. Include schema definitions/migration versions and required roles/configuration. Use a compatible `pg_dump` or supported provider backup, not screenshots of a dashboard.
2. Private object bytes for all originals, localized screenshots, background/element assets and exports, retaining the exact storage keys. Export an inventory of `{assetId, storageKey, byteSize, sha256}` from the same recovery point.
3. Deployment version/configuration references, auth/email/OAuth configuration and a separately protected secret recovery/rotation procedure. Keep actual keys out of the object archive and source repository.

**A Supabase database backup does not include Storage object bytes.** Restoring metadata alone cannot recover deleted screenshot files. Copy storage through the supported Storage/S3 API; do not manipulate `storage.objects` as though it contained file contents. [Supabase backup boundaries](https://supabase.com/docs/guides/platform/backups), [Storage metadata design](https://supabase.com/docs/guides/storage/schema/design)

For a first full logical snapshot, announce maintenance, stop new writes, drain/stop workers, record the cutover time, then take the database snapshot and immutable object inventory/copy. Resume only after both are verified. For continuous backups, document consistency and retention so object deletion cannot race the database recovery point. Encrypt before transfer to the off-site destination and store its integrity manifest separately. Automate this only with approved credentials and destinations.

## Monthly restore drill — isolated target only

1. Create a new isolated test database and a new private test bucket with separate credentials. Never restore over production for a drill. Disable real AI, billing/webhooks, customer emails and external MCP grants on the target. Block outbound effects until state has been reviewed.
2. Restore the chosen database recovery point using the provider's supported workflow or `pg_restore` into the new database. Restore roles/configuration as required. Use the compatible recorded application image first; assess migrations before upgrading.
3. Restore object bytes under their original keys through Storage APIs. Keep the bucket private. Inspect every inventory entry: object exists, byte count matches and SHA-256 matches. Report missing/unreferenced objects rather than deleting them automatically.
4. Verify revision parent references, workspace isolation, memberships, asset ownership and all expected schemas. Compare counts and ledger totals with the backup manifest; confirm no duplicate job debit references and no successful job with an unresolved reservation.
5. With the worker still stopped, inspect queued/running jobs and checkpoint state. Do not replay customer AI or Stripe effects from a snapshot. Use an approved recovery procedure to reconcile remote payment state and retire/hold stale jobs before enabling consumers.
6. In the isolated target, log in as two synthetic users and test cross-workspace denial. Open an editable revision with localized sources and decorative image layers, export it without AI, and compare dimensions, alpha and source/layout behavior with the original. Test a stale expected revision conflict.
7. Record backup timestamp, restoration duration, object count/bytes/hash verification, data consistency checks, export result and outstanding differences. The drill passes only after both data and usable image output are verified. Retain the report under restricted access and remove the isolated restore using approved, explicit-target cleanup.

Before an actual failover, reconcile payments with Stripe, address consent/token revocations that occurred after the recovery point, rotate exposed/affected credentials and signing keys, verify auth callbacks and public origin, and obtain operator approval before restoring outbound traffic or paid jobs. Coordinate customer communication where the recovery point implies lost edits. A backup that has never passed a restore drill is not launch evidence.

### Repeatable local recovery rehearsal and evidence

`server/tests/restore-drill-smoke.ts` is an opt-in **synthetic-only rehearsal**, not a general restoration utility. It requires `APPSCREEN_RESTORE_DRILL_CONFIRM=synthetic-only`, a loopback `TEST_DATABASE_URL` whose database name is explicitly test-scoped, and the exact `RESTORE_DRILL_POSTGRES_CONTAINER`. It compares the container's PostgreSQL system identity to the supplied connection, creates fresh uniquely named databases, and rejects any existing target. There is no `--clean`, DROP, customer dump input, automatic queue consumer, provider credential or production activation path.

The rehearsal closes its synthetic source app, verifies a quiescent recovery point, saves a custom-format PostgreSQL dump and private-object inventory, then reads the persisted set back for restore. The comparison covers table row hashes, migration history, columns/defaults/types, indexes/constraints, RLS flags/policies, effective table/function/schema grants, ownership, views/triggers and sequence state. Effective privileges are compared rather than raw ACL representation: `pg_dump` can normalize an explicit owner-only ACL to the equivalent default. All source/derived object bytes must match their recorded length and SHA-256. The original editable-project ZIP is also opened and every archived source/localization/background/decoration is compared with its original checksum.

The recovered app must preserve two synthetic accounts/workspaces, deny cross-workspace reads and revoked/read-only agent writes, reject stale revision saves, and reproduce a localized/decorated overflow campaign as identical PNGs/ZIP. Copied queued/running AI work and reservations remain dormant and unchanged. Only explicitly created new synthetic export IDs are executed. The temporary active token is revoked in both copies during cleanup; test databases and files are retained, not silently deleted.

Recorded local run: `appscreen-restore-drill-FdN2Q8` under the macOS temporary directory, completed 2026-09-05 UTC (September 4 local time), PostgreSQL tools 17.11. All ten grouped checks passed for 39 tables and 15 objects totaling 3,453,417 bytes. Restoring and verifying that small fixture took 554 ms before application/export checks. This duration is **not a production RTO measurement**. The three store PNGs are opaque 1320×2868; the known original text/device review warning is preserved, not silently cleared by restoration. The full report and exact database names are in the run's `report.json`.

This same-process local rehearsal consumes persisted artifacts but does not simulate losing the host, recovering independent off-site encryption keys, rebuilding managed Auth roles/configuration, or recovering a real private Supabase bucket. Those recovery drills, remote consent/payment reconciliation and the approved RPO/retention policy remain separate release gates.

### Ten-screen capacity and visual review evidence

`server/tests/render-capacity-smoke.ts` uses ten distinct labeled synthetic 1320×2868 sources and the exact Tidal Relay layout. Its four sequential real worker jobs generate editable backup then store ZIP before and after a text-only refinement. Each of the nine overflow handoffs retains canonical geometry, source and frame appearance. Ordered store PNGs are fully decoded, alpha is absent, and archived checksums, CRCs, source pixels, manifests and backup content are checked. Model, payment and external fetch calls are disabled. Nothing runs automatically against a live customer.

Recorded local run: `appscreen-ten-screen-rmXDoN`, completed September 4 local time on macOS/Apple M4 Max/Node 22.22.3. All 183 integrity/behavior assertions passed. The warning-bearing baseline backup/ZIP jobs took 3,471/3,650 ms; refined backup/ZIP took 3,332/3,648 ms. The final ZIP is 6,077,380 bytes and editable backup 1,790,454 bytes. These are local small-fixture observations, not promised customer latency.

Seventy-seven attempted periodic RSS samples recorded a combined Node/descendant-Chromium peak of 1,296,121,856 bytes; individual process-category peaks occurred at different times. Summed RSS double-counts shared pages and includes rehearsal/archive/Sharp buffers; sampling can miss brief spikes and excludes PostgreSQL, other applications and filesystem cache. Do not equate it with container cgroup memory or use it to claim that the configured Linux worker size is sufficient. Measure the pinned image under real storage latency, source sizes/entropy and approved concurrency before choosing capacity or pricing.

The baseline raised six text/device-overlap warnings on screens 2, 5 and 8. A shorter intermediate caption cleared automated warnings but still visibly touched the incoming device; that false-negative is preserved in earlier artifacts. Further copy-only refinement produced visibly separated captions and zero automatic warnings without moving devices. Agent visual review covers the contact sheet and detailed seam images; human quality evaluation with real permission-cleared campaigns and live-provider costs is still required. Automated QA currently tolerates small overlaps and is not a publication guarantee.
